# Обслуживание и диагностика

## Ежедневные команды

```bash
sudo systemctl status ibatyr-apm ibatyr-oap --no-pager
sudo journalctl -u ibatyr-apm -n 100 --no-pager
sudo journalctl -u ibatyr-oap -n 100 --no-pager
curl --fail --silent --show-error http://127.0.0.1:8010/ready
```

Если подключены к ранее установленному серверу, его служба может называться
`skywalking.service`; оболочка не переименовывает и не перезапускает её.
Не публикуйте полный журнал с SQL/адресами/данными клиентов в public Issues.

## Частые проблемы

| Симптом | Действие |
|---|---|
| Port is occupied | Найдите владельца `sudo ss -lntp`; для второй оболочки используйте 8011 |
| 404 на `/api/ai/license` | Вероятно, обращение к старому backend; проверьте порт и путь службы |
| 401 на `/api/ai/...` | Войдите в интерфейс. Это штатная защита API |
| 403 при AI | Проверьте лицензию/CSRF; обновите страницу и повторите анализ |
| Нет сервисов | Создайте нагрузку на приложение, проверьте агент и адрес 11800 |
| SQL отсутствует | Проверьте инструментирование JDBC; отсутствие spans не доказывает отсутствие SQL |
| LLM timeout | Проверьте доступ с сервера оболочки, не только с ноутбука |
| `cryptography` пытается собирать Rust | Обновите pip; используйте binary wheels и поддерживаемый Python/ОС |
| readiness не прошла после установки | Изучите journalctl; файлы оставлены. Повторная установка поверх запрещена |

## Конфигурация

Адрес OAP/порт оболочки задаются в `/etc/ibatyr-apm/shell.env` и unit соответственно.
После ручного редактирования unit: `systemctl daemon-reload` и рестарт оболочки.
Для TLS reverse proxy установите `SW_AI_COOKIE_SECURE=1` и настройте same-origin
проксирование `/ai/` и `/api/ai/`. Готовый публичный HTTPS ingress здесь не устанавливается.

Сессии, AI previews и отчёты в памяти (PDF до часа, максимум 20): только **один worker**; после рестарта нужно войти снова.
Метрики хранятся в OAP storage, не в памяти оболочки.

## Резервное копирование

Из каталога репозитория/дистрибутива оболочки:

```bash
sudo python3 tools/backup_state.py
```

Команда ненадолго останавливает **только `ibatyr-apm.service`** и запускает её
снова даже при ошибке копирования. Вход в UI после рестарта потребуется повторить.
OAP, агенты, Elasticsearch и приём алертов Wazuh продолжают работать.
Это ручной запуск, ежедневный таймер этой командой не устанавливается.

В `/var/backups/ibatyr-apm/ibatyr-state-<UTC>.tar.gz` попадают:

- `settings.json`: настройки AI и API-ключи;
- `users.sqlite3`: пользователи, хеши паролей, роли, блокировки и аудит;
- весь каталог лицензии: `state.json` с UUID и last_seen, подписанная лицензия,
  доверенный публичный ключ (если установлены);
- `shell.env`, unit оболочки, его drop-in конфигурации и конфигурация Nginx
  `/etc/nginx/conf.d/ibatyr-apm.conf`, если эти файлы существуют;
- манифест с исходными путями, UID/GID, правами и SHA-256 файлов.

Пути настроек/лицензии читаются из `/etc/ibatyr-apm/shell.env`. Для нестандартной
установки укажите вместе `--settings /абсолютный/путь/settings.json` и
`--license-dir /абсолютный/путь/license`; при необходимости `--env-file`.
Скрипт не читает shell-команды из env-файла и не выполняет их.

SQLite сохраняется через backup API с учётом WAL, проверяются integrity_check
и наличие активного администратора. Копирование одного файла работающей БД
через `cp` не заменяет этот способ. После упаковки проверяются SHA-256 файлов
в архиве. Повреждённая/отсутствующая БД отменяет копирование; архив не публикуется.
Для старой установки **до появления пользователей** есть явный флаг
`--allow-missing-users`; такая копия отмечается как неполная в манифесте.

Каталог имеет права 0700, архив — 0600. Архив содержит секреты и не зашифрован:
храните его в защищённом хранилище, не загружайте в Git/Issues или дистрибутивы.
Копии автоматически не удаляются; организуйте защищённую внешнюю копию и срок
хранения по правилам клиента. Приватный ключ издателя остаётся у издателя.
Копия на том же диске не защищает от потери сервера.
Метрики/трассировки не входят в архив: отдельно делайте штатные snapshots OAP storage.

`tools/update_workspace.py` теперь автоматически вызывает это копирование после
остановки оболочки **до замены файлов кода**. При ошибке сохраняется прежний код
и запускается прежняя служба; обновление отменяется. Копия кода в
`update-backup-workspace-*` остаётся отдельной. При автоматическом откате кода
пользовательские данные из архива не перезаписываются.

### Восстановление

Сначала проверьте архив на отдельной машине: распакуйте его в закрытый временный
каталог, сравните SHA-256 с `state/manifest.json` и выполните `PRAGMA integrity_check`
для `state/users.sqlite3`. Затем в окно обслуживания остановите оболочку,
сохраните текущее состояние и восстановите **настройки, users.sqlite3 и каталог
лицензии из одного архива** по original_path в манифесте. Удалите оставшиеся
`users.sqlite3-wal`/`users.sqlite3-shm` только после остановки всех процессов,
работающих с этой БД. Восстановите владельца службы и права 0600 на файлах
состояния; каталог лицензии должен оставаться доступным на запись пользователю
службы. Нельзя накладывать старую лицензию поверх нового UUID или запускать
setup_ai.py для замены существующей базы пользователей.

Unit/env/Nginx восстанавливайте только если они действительно повреждены и
после проверки путей/портов для текущего сервера. При изменении unit выполните
daemon-reload, при изменении Nginx — nginx -t. Запустите оболочку, проверьте
/ready, вход, список пользователей и состояние лицензии. Восстановление не
продлевает лицензию и не отменяет срок действия; исторические last_seen/UUID
вручную не редактируйте. Пароли, роли и аудит вернутся к состоянию на дату копии.

## Диагностика локальной LLM

На сервере оболочки, из каталога репозитория/дистрибутива:

```bash
sudo /opt/ibatyr/shell/0.5.0-rc1/.venv/bin/python tools/diagnose_llm.py --chat
```

Скрипт читает только сохранённый профиль `local` из
`/var/lib/ibatyr-apm/settings.json` (другой путь: `--config`). Проверяет `/health`,
`<Base URL>/models` и с флагом `--chat` отправляет **один** короткий Chat
Completions запрос с настроенными моделью, авторизацией и параметром лимита
токенов. Без `--chat` генерация не запускается. Мониторинговые/SQL данные не
передаются, ключ, содержимое настроек и тела ошибок не выводятся. Прокси из
окружения не используются, перенаправления и автоматические повторы отключены.

| Результат | Следующая проверка |
|---|---|
| CONNECT_TIMEOUT | На сервере модели: `sudo ss -lntp '( sport = :8000 )'`; маршрут/firewall от сервера APM, адрес прослушивания |
| READ_TIMEOUT | Очередь, загрузка модели/GPU и журналы сервера LLM; это не доказательство неверного ID модели |
| HTTP 401/403 | Настроенная авторизация и разрешение на модель |
| HTTP 404 на health | Путь может отсутствовать; продолжайте проверку /models |
| HTTP 200 на models | Сравните настроенную модель с точным опубликованным ID, он может быть alias |
| HTTP 400/422 на chat | Совместимость Chat Completions, chat template, выбранный max_tokens/max_completion_tokens; нужны журналы LLM |
| Chat HTTP 200 | Короткий запрос прошёл; это не подтверждает время полного AI-анализа |

При ошибке запроса backend теперь различает connect_timeout (10 с), read_timeout
(100 с без новых данных), write_timeout и pool_timeout. Эти значения не являются
общим дедлайном всего AI-отчёта. На текущем сервере Nginx имеет read timeout
180 с; слепое увеличение одного тайм-аута не исправляет отсутствие сети.

## Обновление / откат

Этот RC поставляет **first-install**, не автоматическую миграцию production.
Прямое изменение existing main.py не выполняется. Для обновления:

1. Поднимите новую версию на стенде/отдельном порту, проверьте приёмку.
2. Сохраните unit, конфигурацию, license state и текущую версию кода.
3. В окно обслуживания переключите unit на проверенный каталог версии.
4. Сделайте readiness и функциональные проверки; при ошибке верните прежний unit.

Не удаляйте `/var/lib/ibatyr-apm/license`: потеря UUID меняет идентичность установки.
Если новая установка прервалась, сначала исследуйте её журнал. Автоматическое удаление
частично созданных каталогов и повторная установка не предусмотрены, чтобы не потерять
настройки. Удалять можно только созданную нерабочую установку после проверки путей.

## Ограничения и данные

Только GENERAL services, до 24 часов за один запрос, пагинация сегментов.
Минутные P95 не являются общим P95. Ошибка span не равна HTTP 500.
Сбор SQL и отправку данных внешнему LLM согласуйте с правилами клиента;
перед анализом UI показывает сокращённые данные. Экспорт trace JSON может содержать
сырые SQL и внутренние адреса; обращайтесь с ним как с диагностическими данными клиента.

## Переход с 0.4.0-rc1 на 0.5.0-rc1

Сначала выполните приёмку новой оболочки на отдельной тестовой VM с тем же OAP.
First-install не обновляет существующую службу. Для штатной установки 0.4.0-rc1
сохраните systemd unit, `/etc/ibatyr-apm/` и `/var/lib/ibatyr-apm/`. Подготовьте новый
каталог `/opt/ibatyr/shell/0.5.0-rc1`, скопируйте туда содержимое `shell/`, создайте
venv и установите requirements. В unit замените только WorkingDirectory и путь к
Python/uvicorn на новый каталог; сохраните EnvironmentFile, порт, пользователя,
license directory и один worker. Выполните daemon-reload/restart, readiness и вход.
При ошибке верните сохранённый unit; старый каталог оставьте до окончания приёмки.

Установка из `~/skywalking-ai/backend` могла иметь другой unit/пути — сначала
проверьте фактический ExecStart. Не используйте generic first-install как upgrade.
Правила алертов переносите по [ALERTS.md](ALERTS.md), сохраняя существующие hooks.
Live не работает в скрытой вкладке. Ошибка обновления сохраняет последний результат
с отметкой об отсутствии свежих данных. AI автоматически не вызывается.

## Суточные графики и лимит 500 минут

На OAP 10.1.0 подтверждён отказ минутных запросов длиннее 500 минут:
`Duration data error ... can't exceed 500 minutes`.
Оболочка делит период метрик на непересекающиеся окна не более 480 минут.
Для 24 часов выполняются три запроса по восемь часов, сохраняется шаг MINUTE.
Ответы объединяются по timestamp; границы окон не считаются дважды, пропуски
не превращаются в нули. KPI вычисляются по объединённым минутам, а не усреднением
трёх окон. P95 остаётся минутным, максимум минутных P95 не является суточным P95.

Не более трёх запросов метрик на запрос dashboard выполняются параллельно.
Общий бюджет получения метаданных и метрик — 35 секунд. Ошибка одного запроса
не выдаётся за успешно загруженные сутки. Недоступность отдельной метрики в окне
отражается пропусками и предупреждением с границами окна.
В JSON dashboard поле `query_plan.metric_requests` показывает число запросов
метрик; для суток ожидается 3, а `coverage.requested_minutes` — 1440.

Для применения этого исправления обновите `shell/dashboard_routes.py` в каталоге
работающей оболочки с резервной копией и перезапустите только `ibatyr-apm.service`.
Изменять ограничения OAP или перезапускать Elasticsearch не требуется.
