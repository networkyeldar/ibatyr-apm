# Обслуживание и диагностика

## Ежедневные команды

```bash
sudo systemctl status ibatyr-apm ibatyr-oap --no-pager
sudo journalctl -u ibatyr-apm -n 100 --no-pager
sudo journalctl -u ibatyr-oap -n 100 --no-pager
curl --fail --silent --show-error http://127.0.0.1:8010/ready
```

Если подключены к ранее установленному серверу, его служба может называться
`skywalking.service`; оболочка не переименовывает и не перезапускает её.
Не публикуйте полный журнал с SQL/адресами/данными клиентов в public Issues.

## Частые проблемы

| Симптом | Действие |
|---|---|
| Port is occupied | Найдите владельца `sudo ss -lntp`; для второй оболочки используйте 8011 |
| 404 на `/api/ai/license` | Вероятно, обращение к старому backend; проверьте порт и путь службы |
| 401 на `/api/ai/...` | Войдите в интерфейс. Это штатная защита API |
| 403 при AI | Проверьте лицензию/CSRF; обновите страницу и повторите анализ |
| Нет сервисов | Создайте нагрузку на приложение, проверьте агент и адрес 11800 |
| SQL отсутствует | Проверьте инструментирование JDBC; отсутствие spans не доказывает отсутствие SQL |
| LLM timeout | Проверьте доступ с сервера оболочки, не только с ноутбука |
| `cryptography` пытается собирать Rust | Обновите pip; используйте binary wheels и поддерживаемый Python/ОС |
| readiness не прошла после установки | Изучите journalctl; файлы оставлены. Повторная установка поверх запрещена |

## Конфигурация

Адрес OAP/порт оболочки задаются в `/etc/ibatyr-apm/shell.env` и unit соответственно.
После ручного редактирования unit: `systemctl daemon-reload` и рестарт оболочки.
Для TLS reverse proxy установите `SW_AI_COOKIE_SECURE=1` и настройте same-origin
проксирование `/ai/` и `/api/ai/`. Готовый публичный HTTPS ingress здесь не устанавливается.

Сессии, AI previews и отчёты в памяти (PDF до часа, максимум 20): только **один worker**; после рестарта нужно войти снова.
Метрики хранятся в OAP storage, не в памяти оболочки.

## Резервное копирование

Сохраняйте защищённые копии `/etc/ibatyr-apm/` и `/var/lib/ibatyr-apm/`, включая
лицензию и UUID. `settings.json` содержит LLM API-ключи. Отдельно делайте штатные
snapshots постоянного хранилища OAP. Не сохраняйте копии в Git.

## Обновление / откат

Этот RC поставляет **first-install**, не автоматическую миграцию production.
Прямое изменение existing main.py не выполняется. Для обновления:

1. Поднимите новую версию на стенде/отдельном порту, проверьте приёмку.
2. Сохраните unit, конфигурацию, license state и текущую версию кода.
3. В окно обслуживания переключите unit на проверенный каталог версии.
4. Сделайте readiness и функциональные проверки; при ошибке верните прежний unit.

Не удаляйте `/var/lib/ibatyr-apm/license`: потеря UUID меняет идентичность установки.
Если новая установка прервалась, сначала исследуйте её журнал. Автоматическое удаление
частично созданных каталогов и повторная установка не предусмотрены, чтобы не потерять
настройки. Удалять можно только созданную нерабочую установку после проверки путей.

## Ограничения и данные

Только GENERAL services, до 24 часов за один запрос, пагинация сегментов.
Минутные P95 не являются общим P95. Ошибка span не равна HTTP 500.
Сбор SQL и отправку данных внешнему LLM согласуйте с правилами клиента;
перед анализом UI показывает сокращённые данные. Экспорт trace JSON может содержать
сырые SQL и внутренние адреса; обращайтесь с ним как с диагностическими данными клиента.

## Переход с 0.4.0-rc1 на 0.5.0-rc1

Сначала выполните приёмку новой оболочки на отдельной тестовой VM с тем же OAP.
First-install не обновляет существующую службу. Для штатной установки 0.4.0-rc1
сохраните systemd unit, `/etc/ibatyr-apm/` и `/var/lib/ibatyr-apm/`. Подготовьте новый
каталог `/opt/ibatyr/shell/0.5.0-rc1`, скопируйте туда содержимое `shell/`, создайте
venv и установите requirements. В unit замените только WorkingDirectory и путь к
Python/uvicorn на новый каталог; сохраните EnvironmentFile, порт, пользователя,
license directory и один worker. Выполните daemon-reload/restart, readiness и вход.
При ошибке верните сохранённый unit; старый каталог оставьте до окончания приёмки.

Установка из `~/skywalking-ai/backend` могла иметь другой unit/пути — сначала
проверьте фактический ExecStart. Не используйте generic first-install как upgrade.
Правила алертов переносите по [ALERTS.md](ALERTS.md), сохраняя существующие hooks.
Live не работает в скрытой вкладке. Ошибка обновления сохраняет последний результат
с отметкой об отсутствии свежих данных. AI автоматически не вызывается.

## Суточные графики и лимит 500 минут

На OAP 10.1.0 подтверждён отказ минутных запросов длиннее 500 минут:
`Duration data error ... can't exceed 500 minutes`.
Оболочка делит период метрик на непересекающиеся окна не более 480 минут.
Для 24 часов выполняются три запроса по восемь часов, сохраняется шаг MINUTE.
Ответы объединяются по timestamp; границы окон не считаются дважды, пропуски
не превращаются в нули. KPI вычисляются по объединённым минутам, а не усреднением
трёх окон. P95 остаётся минутным, максимум минутных P95 не является суточным P95.

Не более трёх запросов метрик на запрос dashboard выполняются параллельно.
Общий бюджет получения метаданных и метрик — 35 секунд. Ошибка одного запроса
не выдаётся за успешно загруженные сутки. Недоступность отдельной метрики в окне
отражается пропусками и предупреждением с границами окна.
В JSON dashboard поле `query_plan.metric_requests` показывает число запросов
метрик; для суток ожидается 3, а `coverage.requested_minutes` — 1440.

Для применения этого исправления обновите `shell/dashboard_routes.py` в каталоге
работающей оболочки с резервной копией и перезапустите только `ibatyr-apm.service`.
Изменять ограничения OAP или перезапускать Elasticsearch не требуется.
